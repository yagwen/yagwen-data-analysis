Agent、大模型上下文、Skill：三者之间的关系

学习深度：入门（综合） ｜ 生成工具：WorkBuddy + concept-learning-generator Skill ｜ 生成日期：2026-09-10 ｜ 配套单概念资料：Agent / 上下文 / Skill

一句话定义：如果把一个 AI 系统比作一位助理，那么 Agent 是"亲自干活的助理"（执行层），上下文是"他此刻桌上摊开的全部材料"（信息层），Skill 是"他抽屉里随取随用的标准手册"（知识层）——三者分别回答"做不做""看见什么""怎么做"，并共同构成一个"看见 → 会做 → 去做 → 沉淀"的协作闭环。

一、概念通俗解释

延续三份单概念资料里的类比，把它们拼成一幅完整的图：

你雇了一位聪明的助理（Agent）。他每次干活时，只能依据办公桌桌面上此刻摊开的东西做判断——桌上有任务说明、相关资料、之前几步的工作记录，桌面之外的东西他一概"看不见"（上下文）。这位助理还有一个抽屉，里面放着一册册标准工作手册（Skill）——你吩咐"整理读书笔记"，他就抽出《笔记整理手册》摊到桌面上照着做；吩咐"做学习资料"，他就抽出另一册。

三者的协作就在这张桌子上发生：

  • 桌面（上下文）是决策的原材料：摊开的资料越对、越清楚，助理的判断越专业；桌上没有的，他只能瞎猜。
  • 手册（Skill）是对桌面的"主动管理"：桌面本身用完就清空，但手册把"什么任务该摊什么资料、按什么步骤做"固化成了文件，随取随用。
  • 助理（Agent）是唯一真正动手的：他基于桌面信息做计划、打电话（调工具）、写文件（执行），把每一步的结果又放回桌面，供下一步参考。

一句话总结三者的分工：上下文决定他能看见什么，Skill 决定他会怎么干，Agent 决定他真正去干。

二、核心机制与组成：三层架构与一个闭环

1. 三层架构：三个概念分别位于 AI 系统的不同层次，不是同一层的竞争关系：

信息层
上下文 Context模型此刻可见的全部信息（系统提示、历史、输入、注入资料），一切的承载基础 知识层
Skill 技能持久化的任务方法论（SKILL.md），触发时注入信息层 执行层
Agent 智能体基于信息层决策、调用工具行动、对结果负责的整体系统

关系机制一句话解释
上下文 → Agent决策的原材料Agent 每一步决策都只能基于当前窗口内的信息；窗口外的事它"看不见"。上下文的质量决定 Agent 表现的上限
Skill → 上下文注入Skill 被触发时全文进入上下文窗口——Skill 不直接"指挥"模型，而是通过变成窗口内容来起作用
Skill → Agent供给方法Skill 给 Agent 提供标准流程，让它的行为稳定、可复现，而不是每次看运气
Agent → 上下文反馈Agent 调用工具得到的结果作为新信息进入下一轮上下文，支撑后续决策（Agent Loop 的"观察"环节）
Agent → Skill沉淀执行中验证有效的新方法写回 Skill，下次直接复用——这是三者形成的经验闭环

4. 三者协作的完整闭环：

用户提出目标 → 匹配 Skill 并注入上下文 → Agent 基于上下文规划 → 调用工具执行 → 结果反馈回上下文 → 循环直至完成 → 有效经验沉淀为新 Skill / 记忆
这个闭环揭示了一个关键洞察：上下文是"流动的"（每轮都在更新），Skill 是"沉淀的"（跨任务留存），Agent 是"驱动的"（让信息流动起来）。三者任何一个缺席，闭环都转不起来。

三、实际应用场景案例

案例：WorkBuddy 完成本次作业的全过程（三者同台的真实现场）

"用 concept-learning-generator 生成【Agent】的学习资料"这一句话，在系统内同时激活了三个概念：

  1. Skill 触发（知识层）：请求匹配到 concept-learning-generator/SKILL.md 的描述，该文件被加载；
  2. 上下文组装（信息层）：系统提示、本仓库的项目结构、Skill 的七板块流程、此前对话的历史，一起进入上下文窗口——模型此刻的"桌面"被摆好了；
  3. Agent 执行（执行层）：WorkBuddy 按流程逐步执行：读取旧版资料、备份、写新文件、打开预览、推送附件、记录工作日志——每一步的工具结果都反馈回上下文，支撑下一步判断；
  4. 经验沉淀（闭环）：任务完成后在项目记忆中记下本次流程，供后续会话复用。

三份概念资料（Agent / 上下文 / Skill）就是这样被"三者协作"生产出来的——这份资料本身，就是它所讲内容的一次现场演示。

四、易混淆之处 & 理解边界

常见误解澄清
"Skill 是 Agent 的一部分"两者是不同层的东西：Skill 属于知识层，不需要 Agent 也能用（普通对话中照样可以触发 Skill）；Agent 属于执行层，没有 Skill 也能工作（只是每次都从零摸索）。它们是配合关系，不是包含关系
"上下文 = 记忆 = Skill，都是让 AI 记住东西"三者角色不同：上下文是此刻的信息载体（临时），记忆是事实与偏好的持久化（跨会话，触发时重新注入窗口），Skill 是方法论的持久化（规定怎么做而非记住什么）
"三个概念里哪个最重要？"这是个伪问题。三者分别回答"看见什么 / 怎么做 / 做不做"，是互补而非竞争关系——就像问发动机、油箱、方向盘哪个对汽车更重要
"三者组合 = 无所不能"错。三者都是在模型能力上限之内做组织与调度：模型本身不具备的能力（如本地模型看图），上下文再满、Skill 再好、Agent 再勤快也无济于事

理解边界与局限：

  • ❌ 木桶效应真实存在：上下文塞满垃圾、Skill 写得含糊、或任务根本不需要多步执行——任何一个环节的短板都会拖垮整体效果；三者协作是乘法不是加法。
  • ❌ 协作本身有成本：Skill 占窗口、Agent 多轮调用费钱费时、上下文膨胀稀释注意力——工程上的原则仍是"能简单就简单"。
  • ❌ 闭环可能沉淀错误：Agent 把碰巧有效（或有错）的方法写回 Skill，错误会被后续所有任务复用——沉淀环节同样需要人工把关。
  • ✅ 正确的分析姿势：看到一个 AI 产品，先分三层问——它的上下文里装了什么？有没有沉淀方法论？要不要自主多步执行？三个问题问完，产品的基本架构就看清了。

七、自测问题

1.【分层】三个概念分别处于哪一层？各自回答什么问题？

上下文（信息层，回答"看见什么"）；Skill（知识层，回答"怎么做"）；Agent（执行层，回答"做不做/怎么落地"）。

2.【机制】Skill 是如何对 Agent 产生影响的？中间经过哪个环节？

Skill 不直接指挥 Agent，而是触发时先注入上下文窗口，成为模型可见的信息；Agent 再基于（包含 Skill 内容的）上下文做决策。中间环节是上下文。

3.【机制】为什么说"上下文的质量决定 Agent 表现的上限"？

Agent 的每一步决策都只能基于窗口内的信息，窗口外等于不存在。窗口里是指令、资料和正确反馈，它就表现专业；窗口里缺信息或有噪声，它只能瞎猜或被误导——模型再强也巧妇难为无米之炊。

4.【闭环】完整说出三者的协作闭环，并指出哪一步是"经验沉淀"。

用户提出目标 → 匹配 Skill 并注入上下文 → Agent 基于上下文规划 → 调用工具执行 → 结果反馈回上下文 → 循环直至完成 → 有效方法沉淀为新 Skill/记忆。"Agent 执行中验证有效的方法写回 Skill"即经验沉淀环节。

5.【辨析】"Skill 是 Agent 的一个组成部分"这句话错在哪？

两者处于不同层次：Skill 是知识层的方法论文件，普通对话（无 Agent 执行）中也能触发使用；Agent 是执行层系统，没有 Skill 也能工作。二者是配合关系而非包含关系。

6.【思考】分析你正在使用的这类 AI 助手：它的上下文里通常有什么？哪些方法论被沉淀成了 Skill？哪些任务真正需要 Agent 式的多步执行？

开放题。参考分析：上下文通常包含系统提示、项目结构、记忆文件、历史对话、Skill 内容；被沉淀的如"概念学习资料生成流程""代码提交流程"；真正需要 Agent 的是步骤无法预先确定的任务（如"修好这个 bug""做出这份报告"），而"翻译这句话"只需单次调用。（言之成理即可）

7.【思考】如果一次任务中 Agent 发现了一个更高效的新流程，写回 Skill 之后被后续任务反复使用——这个闭环有没有风险？如何防范？

有风险：新流程可能只是碰巧有效、适用面窄，甚至包含错误，沉淀后会被后续所有任务复用放大。防范：沉淀前人工审查新 Skill 内容；给 Skill 标注适用范围与验证情况；定期回顾和清理失效技能。
